# Contributor instructions

- Keep changes focused. Follow the boundaries and testing conventions in [design/components.md](design/components.md).
- For release work, read [releases/README.md](releases/README.md). Commit authored notes before tagging; notes must describe the tagged source and assets, not later main changes. Do not rewrite published tags or binaries when editing notes.
- Living docs, code comments and diagnostics describe current behavior and constraints. Version changes and investigation history belong in release notes, commits or PRs. Describe compatibility contracts directly, such as fixed wire identifiers or available verification files.
- Explain outcomes in plain words: state the condition, timing, meaning and any action needed. Define project terms before using them. Meet documentation length limits by removing repetition, not by shortening explanations into jargon.
- Describe sequences as who does what, to which object, and when. Replace phrases such as "durability is bound to progress" with the actual steps and information saved.
- Known issues open with the current protection and resulting behavior, immediately followed by the remaining risk. Then give scope, impact, action and limits; link upstream defects. Put implementation details and test evidence in reference docs. State when frequency is unknown; passing tests do not establish a production failure rate. Avoid broad readiness labels. Keep README known issues in their own section after Install.
  Good: "Startup closes the client on a coordinator timeout so it can exit with an error; slow cleanup can still crash." Bad: "Since v0.2.1, a workaround turns tested timeouts into errors."
- Before finishing edits to docs, comments or diagnostics, reread each changed passage as someone using the current version. Check behavior, scope, impact, action and limits against the implementation; remove prose that requires knowing an earlier version. Include a `Docs review` section in the PR body confirming current behavior first, history confined to release notes/commits/PRs, and source/evidence links consistent with the claims. The CI wording check catches specific chronology patterns; accuracy and clarity still require review.
- Functional tests use Given/When/Then. User documentation stays concise and example-based.
- SQL diagnostics capture positions before advancing tokens. Report safe token categories and fixed syntax hints, without SQL excerpts or input values. Parser/planner changes need exact-location, secret-redaction and fingerprint-compatibility tests; source positions must stay out of persisted query identity.
