# Contributor instructions

- Keep changes focused. Follow the boundaries and testing conventions in [design/components.md](design/components.md).
- For release work, read [releases/README.md](releases/README.md). Commit authored notes before tagging; notes must describe the tagged source and assets, not later main changes. Do not rewrite published tags or binaries when editing notes.
- Living docs, code comments and diagnostics describe current behavior and constraints. Version changes and investigation history belong in release notes, commits or PRs. Describe compatibility contracts directly, such as fixed wire identifiers or available verification files.
- Explain outcomes in plain words: state the condition, timing, meaning and any action needed. Define project terms before using them. Meet documentation length limits by removing repetition, not by shortening explanations into jargon.
- Describe sequences as who does what, to which object, and when. Replace phrases such as "durability is bound to progress" with the actual steps and information saved.
- Keep caveats brief: state the limitation and affected inputs; name the dependency when relevant. Use human-readable ranges where they help users judge applicability, with exact technical bounds alongside or in a linked reference. Link an upstream issue when one exists, not source-code lines. For mitigated failures, state the protection and remaining risk together. Omit mechanism explanations and unrequested workaround advice. Qualify version claims when only configurable defaults limit exposure; do not imply existing records disappear after a broker upgrade. Avoid broad readiness labels. Explain options and caveats beside the usage example they affect; shared prerequisites belong beside the shared setup. Link exact contracts and dependency limits in the references.
  Good: "Shutdown stops at the configured deadline; unsaved records may replay." Bad: a decoder explanation followed by advice to use another tool.
- Before finishing edits to docs, comments or diagnostics, reread each changed passage as someone using the current version. Verify claims against the implementation and evidence; include only details needed to answer the passage's question. Remove prose that requires knowing an earlier version. The CI wording check catches specific chronology patterns; accuracy and clarity still require review.
- Functional tests use Given/When/Then. User documentation stays concise and example-based.
- README covers installation, runnable examples and links to usage tasks. Operating procedures belong in `docs/usage.md`; settings, inspection output, exit codes and metrics belong in `docs/reference.md`; copy behavior and implementation contracts belong in the design references. Move instructions once and link to them; keep one authoritative exit-code table. Follow the documentation budgets in `design/components.md`.
- Review usage docs by walking through preparation, a first run, input forms, stopping, resuming and checking results. State prerequisites and show commands. Validate shell syntax and embedded SQL; use placeholders without contacting example brokers.
- SQL diagnostics capture positions before advancing tokens. Report safe token categories and fixed syntax hints, without SQL excerpts or input values. Parser/planner changes need exact-location, secret-redaction and fingerprint-compatibility tests; source positions must stay out of persisted query identity.
- Each PR needs independent docs, test and simplicity reviewers in the active coding client using its local subscription login. A draft PR may start CI on a frozen commit before source reviews; keep unfinished review fields `Pending` and do not push during those reviews. Mark ready only after all reviews and final-head CI pass, including the changed-line coverage review. Follow the shared [review process](review/README.md); [client setup](design/components.md#local-reviews) covers Claude Code and Codex. Keep scope, evidence and reports locally. After fixes, request follow-up from affected reviewers, including effects on the other aspects; never reuse a stale approval.
- Keep human PR descriptions within 2,000 characters, including comments. Include each template section once. Summarize changes; `Validation` lists only checks beyond CI, or `None`. Review sections contain only `Passed`, `Pending` or `Failed: reason`; only `Passed` is accepted for a ready PR. Do not repeat CI steps/results or successful review details. Dependabot descriptions retain their generated format; the same reviews and CI checks are required. CI checks format, not whether reviews actually ran.
- Prefer deleting or simplifying implementation, tests and docs. Extra layers, options, state or future features need a current requirement, demonstrated failure or compatibility contract. Preserve correctness and useful component boundaries; fewer lines alone do not justify a change.
