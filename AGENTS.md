# Contributor instructions

- Keep changes focused. Follow the boundaries and testing conventions in [design/components.md](design/components.md).
- For release work, read [releases/README.md](releases/README.md). Commit authored notes before tagging; notes must describe the tagged source and assets, not later main changes. Do not rewrite published tags or binaries when editing notes.
- Living docs, code comments and diagnostics describe current behavior and constraints. Version changes and investigation history belong in release notes, commits or PRs. Describe compatibility contracts directly, such as fixed wire identifiers or available verification files.
- Explain outcomes in plain words: state the condition, timing, meaning and any action needed. Define project terms before using them. Meet documentation length limits by removing repetition, not by shortening explanations into jargon.
- Describe sequences as who does what, to which object, and when. Replace phrases such as "durability is bound to progress" with the actual steps and information saved.
- Keep known issues brief: name the affected dependency, limitation and scope. Link an upstream issue when one exists, not source-code lines. For mitigated failures, state the protection and remaining risk together. Omit mechanism explanations, calendar-year conversions and unrequested workaround advice. Qualify version claims when only configurable defaults limit exposure; do not imply existing records disappear after a broker upgrade. Avoid broad readiness labels. Keep README known issues in their own section after Install.
  Good: "Shutdown stops at the configured deadline; unsaved records may replay." Bad: a decoder explanation followed by advice to use another tool.
- Before finishing edits to docs, comments or diagnostics, reread each changed passage as someone using the current version. Verify claims against the implementation and evidence; include only details needed to answer the passage's question. Remove prose that requires knowing an earlier version. Include a `Docs review` section in the PR body confirming current behavior first, history confined to release notes/commits/PRs, and source/evidence links consistent with the claims. The CI wording check catches specific chronology patterns; accuracy and clarity still require review.
- Functional tests use Given/When/Then. User documentation stays concise and example-based.
- README covers installation, runnable examples and essential warnings. Operating procedures belong in `docs/usage.md`; exact contracts, exit codes and implementation details belong in the existing references. Move instructions once and link to them; keep one authoritative exit-code table. Follow the documentation budgets in `design/components.md`.
- Review usage docs by walking through preparation, a first run, input forms, stopping, resuming and checking results. State prerequisites and show commands. Validate shell syntax and embedded SQL; use placeholders without contacting example brokers.
- SQL diagnostics capture positions before advancing tokens. Report safe token categories and fixed syntax hints, without SQL excerpts or input values. Parser/planner changes need exact-location, secret-redaction and fingerprint-compatibility tests; source positions must stay out of persisted query identity.
