# Contributor instructions

- Keep changes focused. Follow the boundaries and testing conventions in [design/components.md](design/components.md).
- For release work, read [releases/README.md](releases/README.md). Commit authored notes before tagging; notes must describe the tagged source and assets, not later main changes. Do not rewrite published tags or binaries when editing notes.
- Living docs, code comments and diagnostics describe current behavior and constraints. Version changes and investigation history belong in release notes, commits or PRs. Describe compatibility contracts directly, such as fixed wire identifiers or available verification files.
- Explain outcomes and sequences in plain words: who does what, to which object, when, under what conditions, and what action is needed. Define project terms. Meet length limits by removing repetition rather than compressing explanations into jargon.
- Keep caveats beside affected examples and shared prerequisites beside setup. State the limitation, affected inputs and relevant dependency; pair protections with remaining risks. Give human-readable ranges and link exact contracts and upstream issues, not source-code lines. Qualify claims that depend on configurable defaults; do not imply broker upgrades remove existing records. Avoid broad readiness labels; omit mechanism detail and unrequested workaround advice.
- Before finishing docs, comments or diagnostics, verify changed claims against implementation and evidence, and reread them as a current user. Remove backstory and details that do not answer the passage's question.
- Functional tests use Given/When/Then. User documentation stays concise and example-based.
- README covers installation, runnable examples and links to usage tasks. Operating procedures belong in `docs/usage.md`; settings, inspection output, exit codes and metrics belong in `docs/reference.md`; copy behavior and implementation contracts belong in the design references. Move instructions once and link to them; keep one authoritative exit-code table. Follow the documentation budgets in `design/components.md`.
- Review usage docs by walking through preparation, a first run, input forms, stopping, resuming and checking results. State prerequisites and show commands. Validate shell syntax and embedded SQL; use placeholders without contacting example brokers.
- SQL diagnostics capture positions before advancing tokens. Report safe token categories and fixed syntax hints, without SQL excerpts or input values. Parser/planner changes need exact-location, secret-redaction and fingerprint-compatibility tests; source positions must stay out of persisted query identity.
- Follow the shared [review process](review/README.md) for reviewer selection, formatting-only exceptions, follow-ups and readiness. Use independent reviewers in the active coding client with its subscription login; [client setup](design/components.md#local-reviews) covers Claude Code and Codex. Keep scope, evidence and reports locally.
- Keep human PR descriptions within 2,000 characters, including comments, with each template section once. Summarize changes; `Validation` lists only checks beyond CI, or `None`. Use the review statuses defined in the shared process; omit CI results and successful review details. Dependabot keeps its generated description but follows the same review process.
- Prefer deleting or simplifying implementation, tests and docs. Extra layers, options, state or future features need a current requirement, demonstrated failure or compatibility contract. Preserve correctness and useful component boundaries; fewer lines alone do not justify a change.
