# Tests review

Review the supplied behavior changes, tests and files used by tests or CI, including documented examples.

- Check that assertions would detect a plausible regression in observable behavior. Flag tests that only execute code, repeat the implementation or succeed after cancellation without verifying completion.
- Separate the behavior under test from routine operations used to arrange, check and clean up. Expected values may be domain-specific; comparing values, checking errors and reporting differences are reusable test infrastructure. Inspect these operations across whole tests and fixtures, including unchanged surrounding code.
- Evaluate reuse at individual sites and as a consistent practice across the reviewed tests and fixtures. Look for shared work hidden behind different names or arguments; do not stop at the most frequent operation. Check directly related fixtures and existing dependencies. State where broader reuse helps and where direct code remains clearer.
- Identify useful gaps in failure handling, boundaries, ownership, progress, ordering, shutdown, restart and compatibility of saved progress, checkpoints and query fingerprints with the previous version. For each gap, propose the smallest useful scenario and its expected outcome. Do not chase a percentage or demand tests for unreachable states, simple getters or trivial pass-throughs.
- Reuse focused fixtures and narrow handwritten mocks or injected ports. Prefer independent component tests; use fewer integration and end-to-end tests for real boundaries. Flag duplication, oversized helpers, excessive setup and unnecessary abstractions.
- Compare direct code, standard utilities, existing dependencies, focused helpers and maintained libraries. For useful candidates, give representative locations, a rough occurrence count and a small replacement. Weigh total writing, reading, debugging, dependency and migration costs; recommend a consistent default and justified exceptions when benefits apply broadly. Failure messages should reveal the failed expectation and observed difference. Preserve behavior, error matching, cleanup and concurrency safety.
- Concurrency tests need observable synchronization and bounded waits; prefer fake clocks to sleeps. Check cleanup, goroutine leaks, race risks and nondeterministic assumptions.
- Collect CI coverage yourself: find the completed run for the reviewed SHA, verify its `headSha`, then download both unit and integration coverage into the permitted evidence cache. Record the SHA, run ID and artifact names. For staged changes, identify which evidence predates them; collect final coverage again after commit and CI. Mark coverage review pending for missing, stale, partial or inaccessible evidence.
- Inspect that coverage, distinguishing Go statement coverage from Codecov line and patch coverage. Sum matching Go coverage blocks across profiles, including repeated blocks; do not overwrite earlier nonzero counts with later zero counts. Passing tests and green CI do not establish adequate coverage.
- For each uncovered changed branch, trace production callers, invariants and supported inputs. Choose explicitly: test reachable behavior, remove unnecessary code, or retain a justified check. Record file/line and evidence for that choice; calling a branch defensive does not justify keeping it. Do not add artificial calls solely to execute unreachable code.
- When Codecov is configured, read its report for the reviewed SHA and the PR patch summary when available. Reconcile every missing and partial changed line with the summed Go blocks. Save the full file/line list, decisions and supporting evidence for the simplicity review; a percentage or selected examples are insufficient. An unreconciled line or inaccessible final report leaves the review pending.
